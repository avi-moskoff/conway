# Conway design language

> **Source of truth.** This file is the source of truth for Conway's design. The [Conway Design System artifact](https://claude.ai/artifact/66YxC7aaGeMee2wacuvDgU) is derived from it (tokens, brand book, preview cards): change the design here first, then re-sync the artifact.

Working reference for how Conway looks, sounds, and behaves — color, type, the physical controls, error handling, motion, and the boot sequence. Captures decisions made through direct conversation, grounded in the actual code (`games/`, `runner.py`, `display.py`, `config.py`). Written up so it can guide implementation and so new screens (a Lorenz attractor, a lightweight fluid sim) can be built consistent with it rather than reopening these questions from scratch.

Two constraints shaped almost everything below: the panel is viewed close enough to resolve individual LED subpixels, and it's an *ambient* object (its own README's word) — nothing should announce itself unless it's telling the truth about something.

## Palette & color semantics

Because the panel is viewed close up, single-channel primaries (pure red, green, or blue) stay visually unambiguous — no subpixel fringing — while multi-channel blends (white, yellow, cyan, magenta) can visually separate into their component colors at very close range. That's fine for larger regions the eye area-averages (ticker text, lines, flocks, trails), risky for an isolated *stationary* single pixel that needs instant identification. **Fast motion defuses it**: a pixel moving quickly (tens of pixels a second) is blended by the eye long before its subpixels can be resolved, so the single-channel rule doesn't bind Langton's ant, boids or a Breakout ball. *Slow* movers don't get the exemption: aircraft and trains on the live screens creep along between polls, spend long stretches effectively stationary, and still need to be single-channel (hence green aircraft, not white). The test is whether the eye can sit on the pixel for a moment, not whether it ever moves. So:

- **Self / home** — marked by inverting whatever's already underneath (the technique `weather_radar.py` already uses for home/landmarks) on every live screen **except the two rail views, where it's a fixed red pixel**. The exception exists because inversion is only safe when the complement of what's underneath doesn't mean something else, and home sits right on the rail line: full-blue line inverts to yellow (the westbound train color, which also read as green-ish like the eastbound one), and a gray line — the obvious neutral fix — was tried and fails the subpixel rule (multi-channel, so it fringes into separate dots up close), while a dim single-channel line was a workaround for a problem a fixed color simply doesn't have. Red is what he expects his house to be. **Markers on continuous fields** (weather home and landmarks) invert the *average of their eight neighbors*, not their own pixel, because a pixel's own inverse can equal its neighbors (gray inverts to gray). If that inverse is within 100 luma of the average, the marker falls back to white or black, whichever is farther (`games.base.invert_neighborhood`). Flight radar's aircraft are green rather than white so the inverted (white on black) home pixel is not mistaken for one. Consequence: on the rail views red means *home*, so the next-arriving train being watched is **white** there instead of red.
- **Red** — reserved exclusively for *signal*: the one thing worth looking at first (closest aircraft, next train). Never reused for home, airport, or error — today's code conflates all four into the same `(255,0,0)`, which only works because those modes never appear together on screen at once. **Exception on the two rail views:** red is home there (see Self / home), so the highlighted next train is white; aircraft mode keeps red for the closest aircraft.
- **Arcade screens (Snake, Breakout)** — red's "the one thing worth looking at first" is the thing you're racing to reach: Snake's food. Breakout's ball is cyan, not red: it's a fast-moving single pixel, so the single-channel rule doesn't bind it (see the motion note above), and the top brick row is red, which would swallow it. Red is never used for *failure* there either: a dead snake blinks in its own colors rather than turning red, and Breakout's lives are green dots, not red ones. Breakout's brick rows are a deliberate exception: a rainbow (red, orange, yellow, green, blue) chosen for arcade character, even though the rows carry no meaning and so spend colors the rest of the system reserves.  Red is spent on the top row for that reason, which is what keeps the ball from being red too. The player's own piece (snake head, paddle) is a multi-pixel region, so white/cyan are fine there. Langton's ant (cyan, 20 steps a second) and Boids (white single pixels) are fine under the same fast-motion exemption. Stationary single pixels on these screens (Breakout's life dots) should still be single-channel, which is why they're green.
- **Green / blue** — categorical (aircraft mode also uses green for every non-featured aircraft: it never shares a screen with the rail views, where green means eastbound) distinctions between multiple simultaneous things on one screen (rail directions, line vs. train, obstacle vs. boid). Never used for signal or error.
- **White / cyan / yellow / magenta** — reserved for larger multi-pixel regions only, never single-pixel identity markers.
- **Error / degraded state** — same invert technique as self/home, but anchored at the fixed corner pixel `(0,0)` instead of center. Position (corner vs. center), not color, is what disambiguates the two. This also frees red/green/blue from ever meaning "something broke," and guarantees visibility against any background field (a fixed color could get lost against a bright AQI or dust field; invert can't).
- **Switcher highlight** — the same invert technique again, applied to a whole row rather than a pixel (see Interaction model → Screen switcher). One convention, three uses now: mark yourself, mark an error, mark a selection — always by inverting, never by a color that could collide with something else on screen.

## Continuous field colormaps

One hue family per field; magnitude is lightness alone (dark = low, bright = high) — no legend to memorize, and inherently closer to perceptually uniform than a multi-hue scale.

- **Conditions (cloud cover + precipitation)** — the one field with two layers, so deliberately not a single-hue ramp. Cloud cover is the base: black (clear) → gray-white (overcast), capped at (150,150,150) rather than full white so a fully overcast panel isn't a wall of light competing with the white ticker text. Precipitation then pushes each pixel from that gray toward pure blue `(0,80,255)`, following the *square root* of rainfall so light rain and drizzle read clearly (a linear 0–4 mm ramp left 0.5 mm nearly black), reaching full blue at 4 mm/h. So: gray/white = clouds, blue = rain, and blue over black = rain under a clear sky. Replaced the original precipitation-only black → blue → white ramp after hardware testing: on a dry overcast day the screen was entirely black and looked broken. Cloud cover comes from Open-Meteo's `cloud_cover` alongside the existing conditions request.
- **AQI** — replaces the EPA's green→yellow→orange→red→purple→maroon scale with black → amber → white. Dropped deliberately: this display is personal/single-viewer, Avi doesn't have the EPA colors memorized anyway, so there's no legibility upside to keeping a non-uniform scale just for convention's sake. Amber was chosen to stay visually distinct from precip's blue, from reserved signal-red, and from the rail screens' categorical green/blue.
- **Dust** — brought in line with the same rule via a filter rather than left as an undecoded raw image. NOAA's Dust RGB product is built purely from thermal-IR band differences (12.3−10.3 µm, 11.2−8.4 µm, and raw 10.3 µm) that run identically day and night — there's no algorithmic day/night switch — but the diurnal heating cycle and plume altitude both shift dust's apparent hue continuously across a purple-plum-to-pink-magenta range, so there's no clean day/night threshold pair to key off, just one wide band to match against. Matched pixels get remapped to **one fixed hue** (consistent with precip/AQI — one hue always means the same thing, rather than preserving whatever shade of purple-to-magenta the source pixel happened to be); everything else gets desaturated to a neutral backdrop. No legend needed once the raw product's color vocabulary (seven-ish categories: dust, several cloud types, desert surface, clear land/ocean) is filtered down to a single "dust, yes or no" signal. Real dust events near Avi are rare (Phoenix haboobs are a monsoon-season, few-times-a-year event), so the threshold can't be fully derived from local capture alone — a starting band is instead seeded directly from the product's own recipe and Quick Guides (CIRA/RAMMB and EUMETrain, cross-checked against each other), rather than left unspecified until a real event comes along:
  - Both guides describe the same continuum this project already assumed: dust reads as **purple/plum at low altitude, shading to pink/magenta with height**, in both day and night scenes, and **very thick plumes go purple regardless of time of day**.
  - That maps to **hue ≈ 280°–355°** (floor raised from 255° after a real evening frame showed the blue-violet moist-airmass wash reading as dust) (spanning purple → plum → magenta → pink), a **saturation floor of ≈ 0.20** (low enough to admit plum's more muted, brownish-purple end, high enough to exclude washed-out white/gray cloud), and a **value floor of ≈ 0.15** (excludes the near-black high, thin ice clouds both guides describe, without cutting off darker nighttime dust).
  - Kept deliberately wide, per the false-alarm-vs-miss asymmetry already established (a false alarm costs a glance; a missed haboob defeats the point of the screen). The one real confusor either guide names is marine stratus — "similar in color to dust, particularly at night" — which isn't a concern for Avi's inland Phoenix-area sector, but is worth remembering if the capture area ever changes.
  - Still a living constant, not a final answer: refine it the next time a real haboob passes over and can be eyeballed against it, the same way the project already treats its geographic dust-sector calibration — but it now starts from the recipe's own numbers instead of from nothing.

## Typography

Moving off `ImageFont.load_default(size=12)` — an outline font, anti-aliased then thresholded to 1-bit, which doesn't sit cleanly in the pixel grid (current code nudges the draw position by `-1` just to make it fit).

- Adopt a genuine bitmap/pixel font in the classic dot-matrix LED sign / transit-ticker genre. Deliberately distinct from Frostline's IBM Plex — Conway *is* a dot-matrix display, not a screen simulating one, so a different typographic voice than the web dashboards is appropriate, not a gap to fix.
- **Monospace**, not proportional — not because proportional text can't be measured (`textlength()` is exact either way), but because the menu needs multiple rows to align into columns (label, value, cursor, indentation), and monospace turns that into a fixed character grid instead of a per-label layout problem. One font family serves both the ticker and the menu.
- **Font: Unscii** (public domain), chosen over Pixel Operator, Press Start 2P, Silkscreen, and Tom Thumb for its terminal/hacker character over a web-pixel-font or arcade-marquee feel — a better match for a Pi doing visible computation than a more decorative option. Two of its native grids cover both jobs the project needs from one family:
  - **`unscii-8`** (8×8) for the ticker and menu — the standard variant, not the `thin`/`alt`/`mcr`/`fantasy` style variants, which swap in PETSCII- or fantasy-console-flavored letterforms that trade plain legibility for character; fine as an accent later, riskier for text that has to read at a glance while scrolling.
  - **`unscii-16`** (8×16) for the boot title only. Unscii has no true bold weight, so the boot sequence's "bold lettering" is achieved through scale rather than weight — at that size on a 64×64 grid the word reads as chunky and emphatic on its own.
  - Avoid `unscii-16-full`: it's the one variant that isn't public domain (GPL, inherited from GNU Unifont for full Unicode coverage). Not needed anyway — ticker/menu text is ASCII only (English labels, callsigns, station names).
- Keep the existing ALL CAPS convention for every label — already true everywhere, and correct at this size since lowercase ascenders/descenders cost rows the format can't spare.
- Generalize the "leading token" color trick already used once in `flight_radar.py`'s ticker (tinting the "W"/"E" in "W ETA 4M" to match that direction's train color) into a standing convention: any label may tint its leading token to a categorical color while the rest stays neutral. Not a one-off hack specific to rail.
- **Text is drawn one glyph at a time** (`games.fonts.draw_text`), never as a whole string. With the installed Pillow, a string containing a space is placed one pixel lower than the same letters without one, so drawing the flight-radar direction letter (`W`/`E`) on its own put it a row higher than the ` ETA 5M` beside it — and clipped its top row. Placing each glyph individually (Unscii is monospace) makes every glyph land on the same rows regardless of its neighbors. Every character advances by one measured glyph width (`glyph_advance`, taken from an "M"), spaces included — never from measuring a space itself, which on the Pi came back far wider than a letter and spread words apart. Text width (for centering and scroll detection) is characters × that advance, for the same reason. Capitals are 7px tall, rows 0–6 of the 8px cell; the ticker and menu both rely on that.
- **Tickers sit at the bottom of the panel**: an 8-row strip (7px capitals plus 1px of margin below), i.e. text on rows 56–62 with row 63 blank and one spacer row above it, leaving 55 rows for the visualization (it was a 12-row strip with the text near the top of it, wasting the rows beneath the text). Both live screens share this via `ticker_height`.
- **Menu labels are capped at 7 characters** — `unscii-8` is monospace at 8px/char, and the switcher keeps 1px of padding on each side of the text (see Interaction model → Screen switcher), so 7 characters (56px + 2px padding) is the most that fits the panel's 64px width; an 8th would run into the border. The menu doesn't scroll text the way the ticker does, so every screen's label has to fit outright: `LIFE`, `ANT`, `BOIDS`, `SNAKE`, `BRKOUT`, `FLIGHT`, `WEATHER`. (`BREAKOUT` is 8 and doesn't fit - first draft overflowed; tests now assert every game's label is ≤ 7.) With all seven screens configured the switcher is exactly full; an eighth screen needs the menu to scroll.

## Interaction model

Three physical inputs (button switch, encoder rotation, encoder push — already wired) and one output (the button's red LED).

- **Encoder push = "commit,"** universally. Opens the screen switcher from any screen; confirms a selection once inside it. Same gesture, same meaning, regardless of context.
- **Screen switcher (the menu)** — a flat list of top-level programs (the animations, Flight Radar, Weather Radar, and whatever's added later). Replaces today's "rotate always switches screens" behavior entirely — this is now the *only* path to changing screens. Rendered as a **vertical list**, one screen per row, top to bottom in the same order they're registered in `runner.py`'s `_default_games()` — not paged or scrollable (seven screens today (five with no home location configured) fit the 64px-tall panel at one row per text line with room to spare; a much longer roster would need revisiting). The currently-highlighted row is marked by **inverting that row** — background and text both flip — the same "mark it by inverting" convention used for self/home and the error pixel, rather than a new highlight color that would need its own justification. Each row is 9px tall — the 7px capitals plus **1px of padding above, below and to the left of the text** — so the text never forms part of the highlight bar's edge when a row is inverted (tuned on the real hardware, where text flush against the border looked bad selected). Seven rows fit the 64px panel. Opening the switcher highlights whichever screen is currently active, not always the first row.
- **Encoder rotate** — context-dependent. Inside the switcher, it moves the highlighted row (clockwise = next row, counter-clockwise = previous; the same sense applies to view-cycling outside the switcher). On this encoder's wiring, gpiozero reported clockwise turns as counter-clockwise, so `runner.py` constructs `RotaryEncoder(19, 18)` — A/B deliberately swapped — rather than flipping signs in software. On a screen with named sibling views (Flight Radar's aircraft / westbound-ETA / eastbound-ETA; Weather Radar's conditions / AQI / dust), rotate moves between those views, replacing today's button-press cycling (`reset()` in both `flight_radar.py` and `weather_radar.py`). On the three ambient animations, rotate has no defined job. **On the arcade screens it is the primary control** (see Arcade screens below).
- **Zoom/radius via the dial** — considered, explicitly dropped. Not worth the complexity, especially since it would compete with view-switching on the one screen (Flight Radar) that has both a `radius_nm` and named views.
- **Button** — unified across every screen as one verb: *give me something new* (with the arcade exceptions below). A fresh random board, a re-centered ant, a scattered flock, or a forced immediate data refresh on a live screen (promoting the incidental poller-nudge already present in today's `reset()` into the button's one consistent job everywhere). **While the switcher is open it means "select"** — identical to pressing the encoder in again, so either hand's control can confirm (changed after hardware testing; it originally did nothing there). It still never means "cancel": there is no cancel, only confirming the highlighted row, which is the current screen if the highlight hasn't moved.
- **LED** — keeps its existing meaning (steady = program running) and picks up exactly one more: blinking, reserved solely for "the menu is open, so the controls mean something different right now." Never diluted with a second meaning (not reused for error/stale states — those stay on the matrix). See Boot sequence for how the LED's timing relative to boot was settled.

### Arcade screens

Snake and Breakout are a new category: *active*, not ambient. The panel is no longer something glanced at; the knob is a controller and the screen is watched continuously. Rules that follow from that:

- **Rotate = steer, with one sense everywhere.** Clockwise is right (Snake turns the head 90° clockwise per click; Breakout slides the paddle right, or swings the aim clockwise). Same wiring and same `cycle_view` hook as sibling views, so the switcher and button behavior are untouched.
- **Button = start/restart.** It stays "give me something new" (restart) with one addition: when a game has a *pre-launch state*, the button leaves it. Breakout's ball waits on the paddle, the knob sets the launch angle (a dim dotted line shows the heading), and the button fires; once the ball is in play the button restarts the game. This is the one place the button is not a single verb, kept because a game needs a "go" and the alternative (a timed auto-serve) takes the decision away from the player. Known hazard: a stray press mid-rally restarts the game.
- **Failure is the game ending, not an error.** Walls and self-collision end Snake; running out of lives ends Breakout. Neither uses red or the corner-invert pixel (those are for degraded *data*). Snake blinks and restarts itself after about 2 s; Breakout restarts to a waiting ball.
- **Playfield is bounded, not wrapped.** Snake's edges are walls and Breakout's are bounces, unlike the ambient screens' torus. Snake plays on a 32×32 grid of 2px cells because single pixels are too small to steer by at that speed.
- **Constant difficulty.** No speed-up or level ramp; frame delay is fixed (Snake 0.15 s per step, Breakout 0.03 s per frame at 1 px/frame).
- **No score readout yet.** The only HUD is Breakout's lives (three green pixels, top-left). Anything more needs text, which these screens don't have a ticker for; revisit if scores are wanted.

## Error & degraded-state handling

Different failures call for different responses, so they get different ticker text:

- `NO INTERNET` — connection-level failure (DNS, timeout, refused).
- `API ERROR` — a reachable service returning an error.
- `THROTTLED` — a rate limit.

This sits alongside the existing, already-correct states: `NO SIGNAL` / `NO RAIL` (stale — no fresh data in a while, error or not) and `CLEAR SKY` (fresh data, genuinely nothing nearby — not an error). Precedence when more than one could apply: staleness wins outright (once data's too old, that's the stronger and simpler signal — a specific reason stops mattering as much as the fact that nothing's come in for a while); short of that, an active error's specific category shows instead of the normal label; otherwise the normal label.

All three failure categories get **equal visual weight** — the same corner-invert indicator from the palette section — because all three are actionable (check the network; wait it out; turn down the relevant `CONWAY_*_POLL_SECONDS`), so none of them can be the quiet one without risking being missed. The pixel stays a generic binary "something's degraded"; the ticker text carries which one and what to do about it.

**Implemented for weather** (`weather/open_meteo.py`, `weather/goes_dust.py`, `games/weather_radar.py`): both clients now raise a `ConnectionError`/`ApiError`/`RateLimitedError` trio instead of one flat exception (`OpenMeteo*` and `GoesDust*` respectively, each `RateLimitedError` a subclass of its own `ApiError` and carrying `retry_after_seconds`, mirroring `air_traffic`'s existing `AdsbLolError`/`RateLimitedError` split). `weather_radar.py`'s `_classify_weather_error()` sorts either client's exceptions (plus any other unexpected exception, bucketed as `api_error`) into `"no_internet"` / `"api_error"` / `"throttled"`, stored per-field (`_conditions_error_kind`, `_aqi_error_kind`, `_dust_error_kind` - `None` when healthy) instead of the old plain booleans. `_live_label()` implements the precedence above. Flight radar's adsb.lol/rail feeds already had a distinct `RateLimitedError` at the client level but don't yet surface it as ticker text the way weather now does - left alone since it was out of this task's scope, not because it doesn't apply there too.

## Motion & pacing

- **Generative screens** (Conway, Langton, Boids) — frame rate is part of each screen's own character, not something to unify. Conway's 0.1s pace suits discrete generations; Langton/Boids' 0.05s suits continuous motion. Future generative screens (Lorenz attractor, fluid sim) should pick whatever pace suits them, not match the others.
- **Arcade screens** — frame rate *is* the difficulty, so it's a gameplay constant, not tuned for look: fixed for the life of a game and never accelerating (Snake 0.15 s per cell, Breakout 0.03 s per frame).
- **Live-data screens** — frame rate is purely mechanical: exactly fast enough for smooth ticker scrolling and (Flight Radar) continuous extrapolation between polls. Never tuned for "feel."
- **Ticker scroll speed** — constant across every screen, independent of the pacing tier above it, so text always reads at the same pace regardless of screen.
- **Data refreshes** snap in silently — no transition or flash on a new poll landing, consistent with this being ambient and with the LED's no-decoration principle.
- **Manual resets** (button press) are an instant hard cut, not a transition — same reasoning.
- A quiet, unplanned consequence worth remembering: (Ambient screens only; the arcade screens have real walls.) Nothing that's "supposed to" run forever on an infinite plane actually does here, because the board wraps. A Gosper glider gun's output eventually wraps around and collides with itself; Langton's ant's highway does the same thing to its own trail. Not a bug to fix — just a property of this being a finite, wrapped board rather than an idealized infinite one.

## Boot sequence

- **Seed**: "CONWAY," rendered in `unscii-16` (the same family as the ticker/menu, just the larger of its two native grids standing in for a bold weight the font doesn't have — see Typography), used as literal Game of Life generation 0. No new simulation logic — `next_board()` unchanged, just seeded with text instead of randomness on the very first boot.
- Deliberately **not** a claim that Life represents the whole object anymore — it's one of several screens now, most unrelated to cellular automata. The word is pure identity/name, not a summary of functionality. (A "table of contents" boot alternative, cycling through every screen, was considered and rejected — Conway-as-mechanism still felt like the right boot moment.)
- A **progress bar** sits beneath the word, made of the same live cells — part of the same seed bitmap, not a separate overlay system. It fills, segment by segment, exactly when a real game finishes constructing — never on a decorative timer. Its target length is the pixel width of the word above it, so no separate outline/track is needed — the word is already the ruler.
- The whole bitmap (word + bar) is **held static** — shown once, then left alone — while the rest of initialization runs. The matrix driver holds the last frame it's given without needing continuous redraws, so this needs no threading, just calling `display.show()` again each time a stage genuinely finishes.
- The moment everything is ready, that same bitmap becomes gen-0 of a live simulation and `advance()` starts being called — the text and bar visibly dissolving into ordinary Game-of-Life activity *is* the ready signal. Nothing appears before it's true.
- Text seed density note (measured via prototype, DejaVu Sans Bold, size 12, 254 live cells): stops being legible within ~5–10 generations, but doesn't die out — settles into ongoing background activity (roughly 120–200 live cells) rather than fizzling to black. Exact numbers will shift now that the real font is `unscii-16` rather than the prototype's DejaVu Sans Bold, but the qualitative behavior — brief legibility, then dissolve into normal activity rather than death — should hold for any similarly-weighted bold font.
- **Scaling rule**: the progress bar's segment count *is* the number of games about to be built this boot — reversing an earlier version of this rule, which tied the bar to a small, fixed number of abstract cost-*category* stages specifically so it wouldn't have to grow with the screen roster. That version undersold the bar badly: with only one real observable stage ("games built") behind three others that are always already done the instant anything can be painted (see below), the bar could only ever jump from mostly-full to full, never move through a real range. Counting one segment per game instead means every screen actually gets its own visible step — a slow one (`WeatherRadarGame`) shows up as a real pause on its segment, not a blended-in fraction of a single lump. It still doesn't need hand-maintaining as screens are added: the count is read off the resolved roster (`runner.GameRunner._default_game_factories`) at boot, not hardcoded.
- **Construction stays eager for every screen**, including ones with real `__init__` cost like `WeatherRadarGame`'s grid precompute (`_build_pixel_grid` / `_build_dust_sector_pixels`, each a `np.vectorize` pass over ~3,264 cells — real Python-loop cost on a Pi Zero 2 W). A lazy-construction split was considered first — expensive screens deferred to first navigation, cheap ones built at boot — but the whole reason to defer work was to avoid a long, unexplained wait at boot, and the progress bar above already turns that wait into an honest, visible signal instead of a silent one. Once the wait itself is truthful, there's nothing left for laziness to protect against, and eager wins outright: every screen's config and network errors surface at boot, every boot, rather than only the first time you happen to visit that screen that session, and there's no lazy/eager special-casing to maintain in `runner.py`. Trade-off to remember: boot time now grows with the *total* number of screens rather than staying flat (the planned Lorenz attractor and fluid sim are cheap enough not to matter, but a future screen as heavy as `WeatherRadarGame` would add real seconds to every boot) — acceptable here because Conway boots rarely (power-up, crash recovery, redeploy) and then runs continuously, so a slower boot is a one-time cost, not a per-session one.
- **Matrix construction happens right after GPIO claim, deliberately *ahead* of the slow game-construction work** — the reverse of an earlier version of this rule, which held that lighting the screen up before everything was ready would make it "just an earlier decoration, not a trustworthy signal." That reasoning conflated two different claims: a *full* progress bar (or the board starting to move) really is a readiness claim, but a *partial* bar is the opposite of one — it's an explicit "still working." There's nothing dishonest about painting an honest partial state early; what actually matters is that the bar only ever shows real completed stages, and the board only starts moving once every stage genuinely is done. Building the matrix early is what makes the partial bar *real* rather than theoretical — without it, nothing exists to paint the partial state onto at all, and the bar could only ever be shown already full. The one stage that stays permanently unobservable is matrix readiness itself: nothing can be painted before the matrix exists, so it's always already done by the time the bar's first frame (0 games built) is shown — not counted as a segment of its own for exactly that reason (see the Scaling rule above).
- **Anything that reads from `/home/avi` must be loaded before the matrix is constructed.** The rgbmatrix library drops root privileges to the unprivileged `daemon` user the moment `RGBMatrix()` exists (`drop_privileges` defaults to on, and `display.py` doesn't override it). After that, an uncached font file can't be opened (PIL reports it only as `OSError: cannot open resource`), and root-created multiprocessing semaphores can't be unlinked. So `games.fonts.preload_fonts()` caches both Unscii fonts right before `MatrixDisplay` is built, and `warm_up_decode_executor()` in `main.py` spawns the decode worker before `GameRunner` exists. Found on real hardware as a crash loop; `tests/test_runner.py` now asserts every font is cached before the matrix is constructed.
- **LED and boot text are separate, honestly-timed signals, kept apart deliberately**: the LED turns on right after GPIO claim (process alive), the static boot bitmap means "booting," and the bitmap starting to move means "ready." Collapsing these into one signal — e.g. holding the LED off until the matrix itself is live — was considered and rejected, since each is independently true at a different moment in the sequence; merging them would make one of the two dishonest for part of it.

**Implemented**: `games/conway.py`'s `boot_seed_board(height, width, completed_stages, total_stages)` renders the word + bar exactly as described above; `boot_seed_frame(...)` wraps that through `GameOfLife`'s own palette into a display-ready RGB frame, needed because the boot screen has to be paintable before any `GameOfLife` instance exists yet to own a board of its own. `runner.py`'s `_default_game_factories()` resolves which screens are configured (env lookups only — cheap, no real construction) and returns constructor thunks without calling any of them, so `_build_default_games_with_progress()` knows the true roster size before building anything. GPIO is claimed first (LED on immediately), then the matrix is constructed and the boot bitmap is painted at **0** of that count — no games built yet — then each factory is called in turn, with a repaint after every single one finishes; the real `GameOfLife` instance is then seeded to the final count via `seed_boot_progress()`, matching the last frame painted, and `run()`'s first loop iteration paints that same board again. So for the ordinary five-game roster with no home location (Life, Ant, Boids, Snake, Breakout) the bar now genuinely steps 0/5 through 5/5 (seven with flight/weather configured: 0/7 through 7/7), each step landing exactly when that game's constructor returns — confirmed by rendering the whole sequence and comparing frames directly, not just by reasoning about it (`WeatherRadarGame`'s grid precompute shows up as a real, visible pause sitting on its own segment rather than blended into a bigger lump). `BOOT_STAGE_COUNT` (`= 4`) is kept only as a default `total_stages` for callers that don't need the real per-boot count, mainly tests exercising `boot_seed_board`/`boot_seed_frame` directly — `runner.py` no longer uses it. This still only applies to the real default game roster (`_default_game_factories()`), never to a caller-supplied `games` list (tests included).
